### 平时如何使用 AI？

我主要把 AI 当成「老师」和「陪练」，而不是答案生成器：

- 学新东西时，先用它建立初步认知。比如做递推题时完全不会，我就先让它讲递推是什么、和递归有什么区别、常见有哪几类题；
- 做题卡住时，我会先自己想。实在想不出来才会去看答案、让 AI 讲思路，然后逐行理解这段代码在干什么、为什么这么写；
- 最后一步最关键：过几天我会在不借助 AI 的情况下把这道题重新写一遍。只有这一步也过了，我才认为这题是自己真的会了。

### 如果 AI 给出的答案明显不对，你会怎么处理？

直接指出来，告诉它「你这说错了，改正过来」，让它自己重新捋一遍。如果它改完还是不对，或者开始绕圈子，我就不会继续跟着它的思路走了，而是自己去查资料（官方文档、OI Wiki 之类）或者换个角度验证，直到自己能把这个逻辑推通。

## AI 辅助记录

### 1. 我遇到的问题

这次报名要求在 GitHub 上完成「Fork → 克隆 → 建分支 → 提交 → 推送 → 提 PR」，而且 CI 会对 PR 做格式校验。这几个操作我原本都不会，实际操作时又连着撞上三个坑：

- 本机 `git` 命令不可用，PATH 里找不到它；
- 好不容易能运行 git，`git clone` / `git ls-remote` 访问 github.com 又直接失败，报 `Recv failure: Connection was reset`；
- 我不清楚仓库 CI 到底校验什么，很担心辛苦填好却因为格式不对被拒。

### 2. 我是怎么向 AI 提问的

我没有只问一句「git 用不了怎么办」，而是把能提供的证据都给了它：完整的报错原文、我已经确认过的现象（`git --version` 能正常输出版本、浏览器能打开 GitHub 页面）、以及我的最终目标（走完 Fork → PR 全流程并且过 CI）。第三个坑我换了个问法——直接让它去读仓库里的 CI 配置文件，而不是问它「一般 CI 会校验什么」。

### 3. AI 的回答有没有直接解决？

部分解决，而且它第一版回答并不好用。它一开始给的是「检查 PATH、重新安装 Git」这类通用建议，但本机其实早就装了 GitHub Desktop（自带一份 git），它没有先看现场就下了结论；网络问题它也先猜「需要科学上网」，而不是先查本机已有的代理配置。真正有用的两点是：它把仓库的 `.github/workflows/validate-submission.yml` 读出来，帮我确定了硬性规则——PR 目标分支必须是 `main`、源分支必须是 `member/2026/<GitHubID>`、**PR 标题和每一个 commit 的标题都必须写成** `member: add-<GitHubID>`、只允许改动 `members/2026/<GitHubID>/` 下的文件；另外它给的那套排查顺序（先确认命令是否存在 → 再确认网络出口 → 最后用真实操作验证）是可以照着执行的。

### 4. 如果没有，我后来怎么继续处理？

按「先看现场，再下结论」的顺序，一条条动手验证：

- 用 `Get-Command git` 确认 PATH 里确实没有 git，然后在 GitHub Desktop 的安装目录和 Downloads 里翻出了两份现成的 git（PortableGit 2.55），不用重新装；
- 直连失败后没有反复重试，而是去查代理配置：注册表里 `ProxyEnable = 0`（系统代理是关的），但 `127.0.0.1:7897` 确实有进程在监听；给 git 显式指定这个代理之后，`git ls-remote` 立刻就成功了；
- 动手写资料之前，先把 CI 的规则抄下来，按规则建分支、定标题；
- 最后用 `git push --dry-run` 这种真实操作去验证权限，而不是「看起来配好了」就当没问题。

结论：AI 帮我省下了大量翻资料的时间，但它第一版答案通常只是「常见情况的猜测」。真正解决问题的是把它当同事用——先让它看现场（环境、配置文件、报错原文）再给结论，然后自己动手验证每一步。
